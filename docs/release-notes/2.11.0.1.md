# 2.11.0.1

Connector revision for **NiFi 2.11.0** against the **Pulsar 4.2.4** client. Java 21.

**Both fixes here are for defects introduced in `2.11.0`. If you are running `2.11.0`, you have
them.** One can park a publisher task indefinitely; the other makes every consumer write failure
take twice as long to recover as it did on `2.10.0.1`. Neither needs a configuration change to
fix — drop in the new NARs.

## Fixes

**`WaitForExclusive` could park a publisher task forever, recoverable only by Terminate (#219).**
`PublishPulsarRecord` with more than one concurrent task and an exclusive *Producer Access Mode*
collided with its own producer pool: `PublisherPool` created a producer for every lease in use at
once, which is exactly what an exclusive mode tells the broker to refuse. With nobody else on the
topic, a processor locked itself out.

| Mode | Before |
|---|---|
| `Exclusive` | about half the FlowFiles to `failure`, citing an existing exclusive producer that was its own |
| `ExclusiveWithFencing` | the pool's producers fenced each other, then every later send from the fenced producer failed |
| `WaitForExclusive` | **the second task parked inside producer creation and never returned** |

Under any mode but `Shared` the pool now holds **one producer per topic**, and a task that finds it
in use waits up to five seconds to be handed the same one. The topic name is normalised, so
`my-topic` and `persistent://public/default/my-topic` are one topic rather than two. `Shared` is
unchanged: concurrent tasks still get concurrent producers.

Also fixed: a lease closed twice was returned to the pool twice, which under an exclusive mode could
hand one topic to two tasks, and under `Shared` put the same producer in the idle queue twice.

**A write failure took 60 s to redeliver instead of 30 s (#218).** The negative acknowledgement added
in `2.11.0` was meant to make redelivery prompt. It did the opposite for anyone on the defaults: a
nacked message is redelivered by *Negative Acknowledgment Redelivery Delay* and by **nothing else**,
because the Pulsar client drops it from the acknowledgment-timeout tracker the moment it is nacked.
With that delay defaulting to one minute and *Acknowledgment Timeout* to thirty seconds, the "ceiling"
was not a ceiling — the message waited the full minute, where `2.10.0.1` redelivered it in thirty.

The default is now **five seconds**, under the ten-second *Acknowledgment Timeout* floor, so every
valid configuration redelivers a write failure sooner than the timeout alone would.

## Behaviour changes

**A dead letter policy now burns through *Max Redelivery Count* about twelve times faster.**
Redelivery is what advances the count, and redelivery is now five seconds rather than sixty. A
transient write failure — a content repository full for ten seconds — that used to be absorbed by a
minute per attempt can push a **perfectly good message to the dead letter topic within seconds**.
If you set *Max Redelivery Count*, raise it, or set *Negative Acknowledgment Redelivery Delay*
explicitly, to keep the retry window your flow had.

Relatedly, the write-failure error is logged once per redelivery, so during an incident it now
repeats every five seconds per message rather than every minute.

**A FlowFile that could not be attempted goes back to the queue, not to `failure`.** When the
five-second wait for a held producer expires, that FlowFile and the rest of its batch return to the
incoming queue with a warning and a yield. Nothing was published and nothing was attempted, so
`failure` would have been a lie. A flow that was hitting #219 and routing those `failure` FlowFiles
somewhere will now see them retried instead.

**A *Negative Acknowledgment Redelivery Delay* longer than *Acknowledgment Timeout* warns rather than
failing validation.** The timeout does not apply to a nacked message, so that combination waits longer
after a write failure than a plain rollback would — worth saying, not worth refusing. A long delay is
a legitimate poison-message backoff, and a flow that set one on `2.11.0`, or pinned the documented
one-minute default, still starts after upgrading.

## Upgrading

Drop in the new NARs; NiFi stays on 2.11.0. Every flow that runs today keeps running.

Three things worth reviewing:

- **If a consumer sets *Max Redelivery Count***, raise it or set *Negative Acknowledgment Redelivery
  Delay* explicitly — see the behaviour change above. This is the one that can lose you good messages.
- **If a consumer logs the new warning** about the delay exceeding *Acknowledgment Timeout*, decide
  whether that wait is intended.
- **If a publisher uses an exclusive *Producer Access Mode* with more than one concurrent task**, it
  was failing or hanging before this release and will now work. Any downstream handling built around
  those `failure` FlowFiles has nothing to catch any more.
